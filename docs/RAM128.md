# 128 MAC 激活 RAM 分段映射（2026-10-24）

分支 `fpga/npu128-ramcompact` 基于已验收的双 bank 版本 `ebf66d6`。
保持两个激活 bank、每 bank 24,576×64 bit、128 INT8 MAC 和原端口协议，
通过分段推断减少物理 RAM 占用。原预装载及资源基线见 [PREFETCH128.md](PREFETCH128.md)。

**原 100 MHz 约束下的最终物理时序、新网表功能回放及总验收均已通过。**
此前因内存不足保存的 `cb90d61` 检查点已恢复工作；该历史检查点的暂停状态保留在原报告中。

## 原因与实现

原生 PDS 的 `apm_drm_hrm_lutram_utilization.log` 显示：上一版每个
24,576×64 bit 数组被映射为 64 个 `GTP_DRM36K_E1`，读写配置均为 **32K×1**。
每位的地址深度被补到 32K，实际只用前 24K；两个 bank 合计占 128 DRM36K。
加上权重的 28.5 和后处理的 2，NPU 总计 158.5，距规划上限 160 只剩 1.5。

本轮把每个 bank 划成三个 8,192×64 bit 数组：

| bank 内字地址 | 段号 | 段内地址 |
| --- | ---: | --- |
| 0–8191 | 0 | 原地址低 13 bit |
| 8192–16383 | 1 | 原地址低 13 bit |
| 16384–24575 | 2 | 原地址低 13 bit |

bank 选择、ready/valid、外部地址和容量完全不变，调用方不需要知道内部段号。
写入只使能目标 bank 的一个段；读取同样只使能一个段。
六位 one-hot 选择标记在 RAM 读输出更新的同一个时钟沿寄存，然后组合选择返回的 64 bit 数据。
padding 或流水气泡不读 RAM，并保持上一次选择，与同步 RAM 的输出保持行为一致。
复位清零选择标记和原有效位，不清除 RAM 内容。

这样不增加读延迟，也不改变五级地址、七拍 MAC、六级后处理或两项结果队列。
段号比较使用先补零再转 `int` 的表达式，沿用已验证的 ADS 无符号扩展规则。
地址 24576 及以上仍不能写入，没有扩大可访问地址或缩减支持的最大 tile。

综合配置已确认六段各为 **16 个 8K×4** 原语，合计 96 个 DRM36K。
hold 修复后的资源表仍为六段各 16 DRM，NPU 合计 126.5 DRM。
收集器保存每段实际资源、原语配置与原始映射日志哈希，避免按逻辑位数估算。

## 数值与周期验证

- 卷积回归 135 个任务、10,074 个输出像素；两个 bank 的全容量和最高读地址均覆盖。
  新增 Ci257/Ci513、16×16、1×1 用例，在两个 bank 中分别跨过 8192、16384 边界，
  同时覆盖非整组输入通道的掩码。全容量 Ci768 的 3×3 用例覆盖三段间反复切换。
- 原算术穷举、RAM 对照、7,333 个 MAC 向量、128 路乘法展开、背压、19 次卷积中止恢复均通过。
- NPU 三种模式、独立后处理、80 次双 bank 专项启动及部分预装载复位恢复通过。
- 图片接口 16 次整图卷积、115,392 个值与独立 NumPy INT64 参考一致，4 个非法请求拒绝。
  整份测试结果与上一版相同：输出哈希、MAC/活动/总周期和分块数逐项一致。
- [完整 Tiny 分块重测](../reports/npu128-ramcompact-profile.json) 覆盖 416/320、三种模式和
  串行/预装载两种驱动，共 12 个场景，全部原始计数器与 `ebf66d6` 完全相同。

416 量化/激活场景保持 30,404,220 个本地装载加卷积周期，100 MHz 换算为 304.042 ms；
320 保持 18,525,998 拍，即 185.260 ms。
上一轮相对串行装载的 18.31% / 16.17% 收益保留，本轮目标是减少资源而非额外加速。
性能场景使用零张量和已配置后处理，不含 DDR/DMA、CPU、非卷积算子或通信；
不是板上时间或完整模型 FPS，未重跑预训练 YOLOX 的检测精度。

## 物理实现与验收

原生工程沿用同一器件和原 FDC：
100 MHz、setup uncertainty 0.2 ns、hold uncertainty 0.05 ns，全部 IO delay 不变。
旧网表的 PASS 不能用于新逻辑，新综合网表重新运行厂商 GTP 四态事务回放。
回放沿用原 480 次 NPU 事务的功能范围；全容量与段边界由上述 RTL 独立数值回归覆盖。
串行空拍压缩不比较性能计数器，计数器和精确周期另由 RTL 回归及完整分块实测核对。

首轮 `npu128-ramcompact-20261024a` 的网表回放通过，但物理验收失败：
setup +0.207 ns，Fast hold −1.817 ns、Slow hold −3.162 ns，未布通 0。
`run_route_optimize.log` 明确记录 `Route-2056: THS is worse than the threshold for hold fix`，
没有进行逐轮 hold 修复。资源已降至 126.5 DRM，但不能据此验收。
[拒绝记录](../reports/npu128-ramcompact-rejected-a.json) 保存失败时序、映射和原始文件哈希。

后续在新工程开启文档支持的 `route -optimize_routing_recovery TRUE`，
并设置 `route_optimize -max_hold_violated_paths_num 100000`。
该参数控制 recovery 分析下 hold 修复可以处理的路径数量，不修改 STA 通过标准；
原来的时钟、IO 延迟、不确定度及检查范围不变。
内存充足后重跑的 `npu128-ramcompact-20261024d` 完整执行，但仍跳过 hold 修复，
其结果与首轮一致，见 [重跑拒绝记录](../reports/npu128-ramcompact-rejected-d.json)。

`npu128-ramcompact-20261024b` 因启动余量不足，未启动原生 PDS。
`npu128-ramcompact-20261024c` 使用收紧后的 2.5 GiB 任务硬上限启动，
在 472.565 秒时因 Windows 提交余量降至 6,418,874,368 字节（低于 6 GiB）停止，
当时处于布局阶段，任务峰值提交 1,895,010,304 字节，尚未进入本轮布线与 hold 修复。
保护器仅终止本任务进程组；未修改或关闭其他应用。

最终工程 `npu128-ramcompact-20261024g` 增加模块位置预规划：

```tcl
place -mode normal -planning_before_place Enable
```

安装版本与随附 Tcl 手册存在参数差异：`e` 工程的 `performance` 模式被工具拒绝，
实际合法值为 `fast/normal`；`f` 工程的预规划布尔值 `TRUE` 被拒绝，
实际合法值为 `Enable/Disable/Auto`。两次均在布局前退出，未生成可验收的布线结果。
生成器使用工具确认的 `normal/Enable`，保留了全部尝试目录及日志。

`g` 的模块预规划将布线前 THS 从 −13,697.689 ns 降到 −4,851.259 ns。
路由优化日志实际进入 `Hold fix to no violation` 和 `Hold fix to threshold`，
最终 THS=0；不是放宽约束或把跳过修复当作通过。

| 原 10 ns 周期下的最终检查 | Fast | Slow |
| --- | ---: | ---: |
| setup WNS | +3.076 ns | +0.214 ns |
| hold WHS | +0.037 ns | +0.044 ns |
| 最小脉宽裕量 | +4.345 ns | +4.040 ns |
| setup / hold / 脉宽违例端点 | 0 / 0 / 0 | 0 / 0 / 0 |

工具估算 Fmax 为 102.1868 MHz；本轮验收频率仍为 100 MHz，不代表板卡实测频率。
最终未布通网络为 0，约束覆盖检查通过，没有时钟经 SRB 普通布线的告警；
导入的全部 15 条约束与原 FDC 逐条一致，原文件 SHA256 也相同。

| NPU 本体资源 | 预装载基线 | 分段且完成 hold 修复 | 变化 |
| --- | ---: | ---: | ---: |
| LUT | 5,299 | 5,451 | +152 |
| FF | 6,507 | 6,513 | +6 |
| APM | 82 | 82 | 0 |
| 等效 DRM36K | 158.5 | 126.5 | **−32（−20.19%）** |

每 bank 192 KiB、总计 384 KiB 的逻辑激活容量保持不变。
NPU 规划上限 160 DRM 下的余量从 1.5 增加到 33.5；这不是集成 SoC 后的空闲资源测量。
测量顶层合计 5,867 LUT、10,759 FF、82 APM、126.5 DRM。
原生完整流程 516.617 秒，Job 峰值提交 2,290,561,024 字节，
最低物理/提交余量分别为 12,868,558,848 / 12,640,673,792 字节。

[暂停检查点](../reports/npu128-ramcompact-checkpoint.json) 是 `cb90d61` 阶段的历史证据，
保留旧数值、周期验证及内存停止原因。最终证据为：

- [新网表 GTP 回放](../reports/npu128-ramcompact-netlist-validation.json)：
  480 次事务、141 份快照、2623 拍，四态回放通过；运行 820.67 秒，采样峰值 RSS 583.6 MiB。
- [布局布线与时序报告](../reports/npu128-ramcompact-implementation.json)：
  原约束的 Fast/Slow setup、hold、脉宽、覆盖、零未布通及实际 RAM 配置全部通过；保存失败尝试收据和原始证据哈希。
- [当前源码总验收](../reports/npu128-ramcompact-validation.json)：
  独立数值、图片、门级、物理及资源规划检查通过；12 组完整分块计数器与原预装载版本完全相同，51 个第三方文件字节不变。

本轮不生成位流、不接板卡、不修改 SoC、第三方代码、模型或软件数值规则，
也不包含布线后 SDF 回放或 CPU/DDR/PLL 集成时序结论。

## 复现

```bash
python3 tools/run_npu_tests.py --build-dir build/ramcompact/npu
python3 tools/run_adam_tests.py --build-dir build/ramcompact/adam
python3 tools/build_image_sim.py --build-dir build/ramcompact/image
# 图片端口测试需要 NumPy；运行保护参数沿用前两轮记录。
python3 tb/check_image_backend.py --simulator build/ramcompact/image/obj/Vadam_conv128 \
  --output build/ramcompact/image-test.json
python3 tools/profile_prefetch.py --build-dir build/ramcompact/profile \
  --executable build/ramcompact/npu/prefetch/Vnpu_conv128
```

每轮使用新的原生 Windows 工程目录：

```bash
python3 tools/pango/stage_implementation.py \
  --synthesis-project "$PDS_WORK_ROOT/work/npu128-timing-20261024b" \
  --work-root "$PDS_WORK_ROOT" --name npu128-ramcompact-new \
  --rtl-validation build/ramcompact/npu/summary.json \
  --routing-recovery --max-hold-paths 100000 --planned-placement
```

Windows PDS 保护器仍为单线程、物理/提交余量各 6 GiB、超时 1800 秒。
首轮 Job 提交内存硬上限 3 GiB；因系统提交余量不足以再次预留 9 GiB，
内存不足阶段曾将任务硬上限收紧为 2.5 GiB，保留 6 GiB 系统余量；恢复后的最终工程使用 3 GiB。
保护器支持小数 GiB；上限或系统余量触发时仍仅停止本任务进程组。
综合完成后对新工程运行 `tools/pango/check_netlist.py`，指定本轮
`--rtl-executable build/ramcompact/npu/measure/Vnpu_measure_top` 和
新的 `--build-dir build/ramcompact/netlist-g`，以及实际 PDS/Icarus 路径。
完整物理流程及网表验证完成后：

```bash
python3 tools/pango/collect_implementation.py --project "$PROJECT" \
  --netlist-validation build/ramcompact/netlist-g/summary.json \
  --output build/ramcompact/implementation.json
python3 tools/collect_throughput_validation.py --build-dir build/ramcompact \
  --netlist-validation build/ramcompact/netlist-g/summary.json \
  --implementation build/ramcompact/implementation.json \
  --profile build/ramcompact/profile/summary.json \
  --reference-implementation reports/npu128-prefetch-implementation.json \
  --reference-profile reports/npu128-prefetch-profile.json \
  --output build/ramcompact/validation.json
```

汇总器要求实际 RAM 减少、APM 不变、原约束不变、每段实际配置与资源相符，
并且全部 12 个场景的计数器与参照一致。任一条件失败都不会生成 RAM 优化 PASS。
